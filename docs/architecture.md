# Architecture: where everything runs

Most of this project's bugs have had one cause: code written as if it ran
somewhere other than where it runs: a thread using the event loop's database
connection; a module imported twice because it was started with `-m`; a new
worker running the old one's job because both thought they were the only one.
This document is the map. Read it before changing anything that crosses a
process boundary; `docs/protocols.md` is the rules that follow from it.

## One machine

Steve runs on the user's Windows computer, in their account, and does
everything there: Gmail, Calendar, Drive, Tasks, Outlook, memory, the people
ledger, approvals, and the Signal device (signal-cli, linked to
their phone). It has no inbound port.

## Accounts and the connector slot

How a tool reaches one of the user's accounts:

1. **A module** is a folder under `modules/` with a `manifest.toml`: the
   classes it serves (mail, calendar, files, tasks), how it is set up, the
   hosts it reaches, and an engine for each class. `steve_sdk/manifest.py`
   parses it and refuses what it does not know. `core/modules.py` keeps the
   accounts the user added, each of one module, and switches them on and off.
2. **The slot,** `agent/connectors.py`, holds each class's accounts: those
   added, of modules that are on. A tool asks the slot, never a provider by
   name. `ask_all` asks every account at once; an item's id
   (`steve_sdk/ids.py`) names its class and account, so `by_id` takes a
   change back to the account that handed the item out.
3. **One shape per class** (`steve_sdk/classes.py`): a message, an event, a
   file and a task look the same from every account. A provider says what
   it cannot do (threads, flags, a conditional write) rather than faking it.
4. **The engines** build a provider from the account's settings and its
   context: IMAP and SMTP (`core/engines/imap.py`), CalDAV
   (`core/engines/caldav.py`), a calendar's link (`core/engines/ics.py`), an
   MCP server (`core/engines/mcp.py`), or a module's own code: a
   built-in's in core's process (`core/engines/code.py`, for Google's
   client and Outlook's COM), and one from outside in its sandbox
   (`agent/modconnect.py`). The
   context (`core/modctx.py`) is a module's only way out: `ctx.http` and
   `ctx.tcp` to the manifest's hosts, `ctx.com` to its listed members, and
   its secrets from the Credential Manager (`core/credstore.py`).
5. **Core's write path** (`core/writes.py`): every change goes to one exact
   target, on condition that it is as it was read, or after a card. A
   message is sent only on its card or the monitor's verdict that it is free.

Where each provider lives:

| Account | Module | Mail | Calendar | Files and tasks |
|---|---|---|---|---|
| Gmail with an app password | `modules/gmail_password/manifest.toml` | the IMAP engine | the CalDAV engine | none |
| iCloud, Fastmail, Yahoo, Other | `modules/imap/manifest.toml` | the IMAP engine | the CalDAV engine (Other only with a calendar's address) | none |
| Google Cloud | `modules/google_cloud/provider.py` | Gmail's API | Google Calendar | Drive, and Google Tasks |
| Outlook (classic) | `modules/outlook_classic/provider.py` | Outlook over COM | Outlook over COM, read only | none |
| Outlook.com | `modules/outlook_mcp/manifest.toml` | the MCP engine | the MCP engine | none |
| A calendar's private link | `modules/ics/manifest.toml` | none | the ICS engine, read only | none |

## Processes on the laptop

```
the desktop app (ui/src-tauri)     at the user's login, in the tray; one job object
  └ supervisor  python -I -B -m core.supervisor :<chosen>  windowless console
      └ worker(s)   python -E -s -B -m agent.server :<held by the supervisor>
            └ docker, PowerShell, signal-cli
```

| Layer | Judges | By | If it fails |
|---|---|---|---|
| App | the supervisor answers | `POST /_sup/prove` (the supervisor's own), every 30 s | ends it after four misses; starts it again, at most five times in ten minutes |
| Supervisor | the worker serves | `GET /health` on the worker's port | replaces it from the same code, backing off if it keeps failing |

Each layer judges **only the layer directly below it**. A keeper the app
replaced once probed the worker's `/health` and killed a supervisor that was
busy rolling back.

The app owns the tree (`ui/src-tauri/src/backend.rs`): the supervisor starts
suspended, inside a kill-on-close job object, so the app's end, a crash
included, ends everything below it. Quit asks `POST /_sup/stop` first, so the
workers drain. See `docs/always-on.md`.

In an install, the app first checks the tree against `manifest.json`, the
list of every file under `backend\` and `runtime\` with its SHA-256, which
the build signed with the update key
(`ui/src-tauri/src/integrity.rs`, written by `devtools/package.py`'s
`manifest`). Every file is hashed before the backend starts, and any module,
DLL or `.pth` under `backend\` the build did not ship is looked for
(`before_start`). A list the key did not sign, of another version, or naming a changed
or missing file refuses the backend, and the app says which file, with Repair (`ui/src/Power.tsx`).

Steve's installer is Tauri's, per user. Its hooks (`ui/src-tauri/windows/hooks.nsh`)
put Steve in `%LOCALAPPDATA%\Programs\Steve`, never in `%LOCALAPPDATA%\Steve`,
which Tauri would choose and which is an install's data folder.

Updates come through Tauri's updater (`ui/src-tauri/src/update.rs`), at start
and once a day unless the user turned the look off, and install only on their
Install. The address it asks is step 12's: `ui/src-tauri/tauri.conf.json`
names none yet, so a look ends in "Updates are not set up in this build."
The updater offers only a newer release, checks its signature and
that the version signed is the one announced, stops the backend and waits
up to ten seconds for its job to empty (`Backend::stop_for_update`), then
runs the installer, whose pre-install hook (`ui/src-tauri/windows/hooks.nsh`)
deletes the old `backend\` and `runtime\` before it copies. Repair, offered
when the files are damaged, is the same path taking this version's own
installer.

### Blue-green swaps and the duties

`POST /_sup/swap` starts a new worker, waits for it to answer `/health`, flips
traffic to it, then drains and stops the old one. For up to ~40 s two workers
are alive. Everything that must happen exactly once is a **duty**, held by one
worker at a time:

- the Signal device, and the Telegram bot's polling
- the job queue (claiming jobs)
- the microphone and speakers
- every background loop: the heartbeat, reminders, attention, night, wake
  alarm, reflection sweep, action expiry

The supervisor starts workers on standby (`STEVE_STANDBY=1`), and after the
flip calls `POST /_retire` on the old worker, *then* `POST /_activate` on the
new one. The watchdog activates a serving worker it finds still on standby.
A worker started by hand activates itself. Jobs record their claimant
(`jobs.claimed_by`, pid and start time); a job is requeued only when its
claimant is dead. `/health` reports `duties`.

The worker's control routes (`/_shutdown`, `/_activate`, `/_retire`) are called
by the supervisor on the worker's own port; the supervisor's proxy refuses
them from outside.

## Runtime contexts

The same module can run in several of these. Know which before touching
globals, threads or secrets.

| Context | What it is | Has | Does not have |
|---|---|---|---|
| APP | the Tauri shell, in Rust | the job object, the run file, the token | any agent state |
| SUPERVISOR | one asyncio loop | worker handles, the run file | the agent's database, secrets |
| WORKER | `python -m agent.server` as `__main__` | `agent.runtime`: `conn` (loop-thread SQLite), `signal`, `voice`, `jobs`; the duties | — |
| WORKER-THREAD | `asyncio.to_thread` from the worker | whatever it was passed | `runtime.conn` (thread-bound), the loop |
| NIGHT | the worker's 3 a.m. loop | a budget | a human watching |
| CLI | `python -m agent.<module>` by hand | the environment of the shell | `agent.runtime` (all `None`) |
| TESTS | pytest in-process; gate supervisors in a sandbox copy of the tree | temporary databases | anything live (see `tests/unit/conftest.py`) |

started from another checkout (a worktree, the gate sandbox) keeps all of this
inside that checkout.

## Channels and approvals

Signal (signal-cli on the laptop) or Telegram (the user's bot), the tray
(websocket through the supervisor) and desk voice all reach the same
conversation loop. Anything
outward or irreversible is **gated**: `agent/approvals.py` records a card and
puts it in the outbox ("Reply YES MAPLE"), which shows it in the app and
sends it to their phone (flow 3). Only the card says its word: no model
is sent a waiting card's word, in its instructions, its history or a
tool's result (`agent/provider.Unworded`), and `agent/cardwords.py` takes
it out of the model's replies and every other message to a channel, so no
reply can pose as a card. Approvals are decided only by code
that runs **before any model** — `worker/answering.intercept_approval` — and
only for the user's own channels (`core/call_policy.PRESENT_CHANNELS`). The
cards one turn makes for the same tool and account are held until the turn
ends and asked as one card (`approvals.held`), approved whole or in part. A
card keeps the digest of what it showed and the item's identifying field
(`agent/toolset/oncard.py`, `bound`), and the write reads the item again
before it acts (`core/writes.py`): an item changed since, or another in its
place, is asked about again.
What the check after a write finds is said as written and never asked
again, since a second yes would write twice (`AfterWrite`).
On an account that cannot write on condition, that card is the condition,
unless Jev, asked in the user's own conversation, is sure it is not needed
(`core/lostupdate.py`, through `actions._judged`).
The rest of the trust map is `docs/security-model.md`.

## Frozen paths

`core/policy.yaml` names the **frozen** paths (`core/**`, `tests/gate/**`,
`auth/**`, `pyproject.toml`, `uv.lock`, …): never changed by the agent, and
hash-locked in `core/policy.lock`, which the supervisor and `devtools.check`
check. The coding pipeline's roles may not write them
(`core/coder/workspace.coder_may_write`). Agent-initiated self-upgrade is
**off** by default (`self_upgrade.agent_initiated: false`): until it is turned on,
only the user asks for a module build (docs/self-upgrade.md).

## Localhost

The supervisor and every worker refuse any request whose `Origin` is not the
app's, any `Host` that is not a loopback name, and any request without this
start's token (`core/localonly.py`). The supervisor listens on a port the
system chooses at each start, and names it with the token in a run file only
the user can read (`core/localapi.py`). The app has the backend prove it
holds the token before sending it anything; `python -m core.localapi get
/_sup/health` does the same from a shell.
